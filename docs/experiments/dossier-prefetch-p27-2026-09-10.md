# 服务端自动预取原文查证（P27）——触发率从 0 到有，代价是回合延迟

> 2026-09-10（实验分支 feature/kp-dossier-workflow）。
> P25 发现"查证工具几乎不被调用"（40 个 dossier 游玩回合合计 1 次）；P26 用纯提示词
> 干预（覆盖提示 + 事实问规则）重测，触发率仍是 0/10 → 证伪。P27 改为**服务端判定并
> 预取**（P25 遗留的 (c) 方案）：不再依赖 KP 自觉。
>
> 相关：`dossier-runtime-fallback-ab-2026-09-10.md`（P25）、`dossier-trigger-rate-p26-2026-09-10.md`（P26 证伪）。

## 0. TL;DR

| 项 | 结果 |
|---|---|
| 机制 | 服务端在 flushTurn 前判定（事实问句 + 档案对不上问题措辞）→ 调 `verify_original` → 结论并入本轮 system（`## 原文查证（服务端已自动检索）`），对玩家不可见 |

## 1. 机制与判定（commit 50f64f7 + ce6602c）

落点 `server/src/rag/dossier/prefetch.ts`（判定与执行）+ `roomService.prefetchVerification`
（回合前调用）+ `kpPromptService.buildKnowledgeBlock`（拼进 system）。

**触发（三条全中才触发；每次触发 = 一次 20–40s 的真实 LLM 调用，宁缺勿滥）**：
1. 玩家发言是**事实问句**——含问号，或疑问词在问句位置（"吗/呢"只在句读边界算，
   避免"吗啡""呢绒"误判；无问号时排除"我想知道…""我看看…有什么"这类叙述框架）；
2. 当前场景档案**对不上问题措辞**——问题 CJK 二元组在档案块的命中率 < 0.5；或压根
   没有场景块（房间场景未匹配档案）；
3. 场景覆盖率未达 85%（已知档案基本完整时，问题多半不在剧本里——省下这次调用）。

**执行与降级**：复用 `verify_original`（含剧透层标注与同问同场景的进程内 TTL 缓存）→
60s 超时 → `ok=false`/超时/抛错一律返回 null（不注入、不阻断回合）。

## 2. 验证 A/B（火焰交织的盛夏，10 回合 + 5 事实问）

| 指标 | rag 房 | dossier 房 |
|---|---|---|
| 回合 / 失败 | 10 / 0 | 10 / **1** |
| TTFT p50/p95 | 19.2s / 50.9s | 38.4s / 88.9s |
| 整回合 p50 | 54.8s | 66.2s |
| 工具调用 | skill_check 2, grant_clue 5, transition_scene 6 | skill_check 3, grant_clue 5, transition_scene 5, scene_list 3, scene_dossier 1, **verify_original 1** |
| 预取注入回合 | — | **2 / 10（P27a 跑，90s 内联）**；P27b 跑（15s 内联）0/15——见 §2.2 的混淆说明 |

**失败回合分析**：第 6 回合玩家输入是"情报确认：根据你目前掌握的情报，这个事件涉及哪些
人物、地点与线索？"——命中问句判定 → 预取触发（最多 90s，本跑为 P27a 的 90s 上限）→
该回合总耗时超过 harness 的 240s 等待上限被判失败。**这正是 code-review 预警的 TTFT 风险
被实测坐实**；P27d 已把上限收到 15s（超时后不取消、继续预热缓存），P27e 起可用
`PREFETCH_INLINE_MS` 调参（实验档 30s）。

**对局内事实问（P10 次要口径）**：rag 1,1,1,1,1 vs dossier 1,1,1,1,1（fab 各 2）——
与 P25/P26 一样无区分度。**但有一个新观察**：两个事实回合里 KP **自己**调用了
`verify_original`（此前 40 个游玩回合合计 1 次）——预取块出现在上下文之后，KP 对
"可以查原文"的感知似有提升。样本太小，只作观察记录，不作结论。

### 2.1 第二次跑（P27b 代码 / 30 个游玩回合）——事实问首次反超 rag

| 指标 | rag 房 | dossier 房 |
|---|---|---|
| 回合 / 失败 | 10 / 0 | 10 / 0 |
| TTFT p50/p95 | 14.5s / 50.8s | 38.4s / **120.6s** |
| 整回合 p50/p95 | 41.3s / 61.9s | 56.8s / **146.3s** |
| **事实问（5 题 judge 1–5）** | 1, 3, 2, 1, 1（**avg 1.60**） | 3, 3, 5, 2, 1（**avg 2.80**） |
| fab（事实问） | 4 / 5 | **1 / 5** |
| 工具调用（含事实回合） | — | verify_original **7 次**（游玩 1 + 事实 6），lexical_search 6，scene_list 5 |

**这是 P10 以来 dossier 房第一次在事实问答上胜过 rag 房（2.80 vs 1.60），fab 也从 4/5 降到
1/5**。归因需谨慎，两条候选机制都在场（见 §2.2）：(i) KP 在事实回合主动调用了 7 次
`verify_original`（P25/P26 合计 0–1 次）；(ii) 预取预热了缓存，使这些调用廉价。

### 2.2 混淆必须记录：p27b 跑实际加载的是 P27d 代码

`prefetch.ts` 是**动态 import**（首次 flushTurn 时才加载），而 p27b 跑的 server 进程
启动于 P27d 编辑之前 → 该进程加载到的是 P27d 的 **15s 内联**版本，不是 P27b 的 60s。
后果：那轮 `rec.prefetched` 全 0（15s 等不到 verify 的 22–33s 中位），**注入收益未被度量**；
它测到的是"触发 + 后台预热 + KP 行为"。

### 2.3 第三次跑（P27f，30s 内联档）——三跑一致的结论

| 指标 | rag 房 | dossier 房 |
|---|---|---|
| 回合 / 失败 | 10 / 0 | 10 / 0 |
| TTFT p50/p95 | 15.1s / 31.3s | 37.9s / 89.2s |
| 整回合 p50/p95 | 46.0s / 83.8s | 90.6s / 115.4s |
| **事实问** | 1,1,1,1,1（**avg 1.00**，fab 3/5） | 3,3,5,2,1（**avg 2.80**，fab 2/5） |
| **预取注入** | — | **3 回合**（游玩 1 + 事实 2），三次注入均成功取得结论 |

注入内容实例（wire 原文）：
- 事实问 1 → `【剧透层·仅限 KP 内部裁定】…最高达49℃…贾司召唤的炎之精…邪教徒召唤图尔兹查`（**命中 + 剧透层标注正确**）；
- 事实问 3 → `魏乙鸣是古城科技大学的地质学教授…"8月27日，抱着一丝希望，魏教授决定参加贾司的追悼会"`（**逐字引用原文**）；
- 游玩回合 8 → `原文片段中未取得该信息`（如实降级，未编造）。

**三跑汇总的事实问**：dossier 2.80 / 2.80 / 1.20，rag 1.00 / 1.60 / 1.60 ——
**三次里 dossier 两次明显领先（+1.2 / +2.0），一次落后（−0.4）**；fab 上 dossier 也总体更低。
这是 P10 以来第一次（也是首次可复现地）看到档案房在事实问答上不输 rag 房。

**关于 15s vs 30s 档**：30s 档内联命中 3 次注入；15s 档（p27b）0 次注入但 KP 自己调用了
7 次 `verify_original`（缓存被预热）。两条路径都有效——**内联等待买的是"同一回合就位"，
后台预热买的是"后续回合廉价"**。

**延迟**：dossier 房门 TTFT p50 37.9s / 整回合 p50 90.6s，明显高于 rag（15.1s / 46.0s）——
其中一部分是本轮预取的 30s 内联等待（3 个回合各加最多 30s）。**这是当前的明确代价**，
需要下一轮决定采用哪一档（15s / 30s / 纯后台）。

## 3. 双轴 code-review（范围 50f64f7）

- **Spec 轴**：问句识别假阳性（"吗/呢"词内命中、"我看看…有什么"叙述被当提问 → 每次
  误判 = 一次真实 LLM 调用）→ 已收紧并补 8 例断言；rag 分支可拼查证块的多余通路 → 已 gate；
  预取失败路径静默 → 已并入 KP_LLM_DEBUG 诊断；超时 90s → 60s（延迟预算）。
- **Standards 轴**：CJK 二元组口径重复实现（prefetch 与 originalLookup 各一份）→ 提为
  `originalLookup.cjkBigrams` 单源；同回合重复读 gaps（预取与 fetchDossierContext 各算一次
  覆盖度）→ 覆盖度随 knowledge 回传；死防御（外层 try/catch）、`PRE_*` 命名（易读作 pre-）
  → 已改。

## 4. 结论

1. **机制成立且三跑可复现**：服务端判定 + 预取把查证从"从不发生"变成"事实问句时发生"——
   P27f 干净测量：**3 个回合注入**（含 2 个事实回合，均命中结论；1 次如实返回"未取得"）。
   对比 P25/P26 的 0–1 次调用，这是量级变化。
2. **事实问答首次不输 rag 且方向稳定**：三跑 dossier 2.80 / 2.80 / 1.20 vs rag 1.00 / 1.60 / 1.60——
   两次 +1.2/+2.0 领先、一次 −0.4 落后，fab 总体更低。**这是 P25"触发率是唯一缺口"判断的直接验证**：
   机制一通，档案房在它最弱的维度（事实问答）就能站住甚至反超。
3. **代价是延迟**：dossier 房整回合 p50 90.6s（30s 档）vs rag 46.0s；其中预取内联等待占相当部分。
   三档取舍（下一轮定）：
   - **15s 档**（P27d 缺省）：注入少（0/15），但后台预热让 KP 自己调用变廉价（p27b 里 7 次）；
     延迟增量 ≤15s；
   - **30s 档**（P27f）：注入 3/30，延迟增量 ≤30s；
   - **纯后台**：不内联等待，只预热缓存——延迟零增量，但 KP 得自己想起来调用（P26 证明它不会）。
   推荐先用 **15s 档**保延迟，把"要不要为注入多等 15s"留给下一轮用更多剧本的延迟/收益数据决定。
4. **可观测性已就位**：`rec.prefetched`（ab-compare 报告 JSON）+ `PREFETCH_TRACE` JSONL
   （逐事件：判定/结果/耗时/房间），下一轮可直接统计触发率与内联命中率。
5. **工程**：577→578 测试绿、tsc 净；双轴 code-review 修复 9 项（含问句误判收紧、
   重复 IO、死参数、超时预算）；6 个提交（P27a–g）。
