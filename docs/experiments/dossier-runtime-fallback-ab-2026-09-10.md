## 1. 工具设计与实现

落点 `server/src/rag/dossier/originalLookup.ts`（核心 + 注入缝）、`shared/tools/storyLookupTools.ts`
（工具声明，第 4 个）、`server/src/services/roomService.ts`（`buildStoryLookup` 分支接线）。

**输入**：`{ question: string, scene?: string }`。`scene` 缺省 = 房间当前场景（服务端注入）；
跨场景/全篇问题可留空走全篇兜底。

**定位（纯函数，无 LLM）**：
1. 场景级：`coverageGaps.sceneAnchors[当前场景].starts[]` → 每锚开窗 `[start−300, start+2500]`
   （与 P21/P23 的 `ANCHOR_LEAD/ANCHOR_WINDOW` 同口径），并并入与该场景范围相交的 gap span
   （档案丢掉、但属该场景的原文段）；
2. 补足：按问题 CJK 二元组得分追加全篇锚点/gap 窗口（`start:end` 去重），直到吃满 12k 字符预算
   ——首轮实测场景窗口只有 4k，空着 8k 预算会白丢跨场景原文（P21/P23 已证其价值）；
3. 兜底：场景窗口对问题零词面命中 → 全篇词面定位（tier=global）；两者都无 → `tier=none`，
   工具返回「未取得」让 KP 如实叙事。

**作答**：一次**全新上下文** LLM 调用（system=原文问答器 + user=原文窗口+问题），要求只依据所给
片段、输出 `{answer, quote, found}`；`quote` 必须是逐字摘录。渲染上限 580 字符——
kpTurnService 对工具结果做摘要 + **600 字符截断**，工具内容设计上就落在截断线内（设计约束）。

**剧透 gate**：真相/结局类问句（词面信号）、或所选窗口与某条 `truths[].revealScene` 的锚点相交
→ 输出前缀「剧透层·仅限 KP 内部裁定，禁止向玩家复述」——**降级标注而非拒绝**（KP 需要它裁定
"现在能不能给线索"；硬拒绝会让 KP 只能瞎猜）。口径同步写进工具描述与 kpPromptService 的知识源说明。

**缓存与降级**：`userId:scriptId:scene:question → 内容` 进程内 TTL 10 分钟（一局内原文/档案静态），
上限 200 条；原文读取同样 TTL 缓存（PDF 走 OCR，逐次读不可行）。原文缺失 / 定位不到 / LLM 失败或空答
→ 「未取得」文本，**永不抛出**（回合不因查证失败中断）。

**已知坑（P25a 修）**：子调用初版 `max_tokens=1200` 对推理模型过小 → 2/5 空响应（reasoning 吃光预算）、
1/5 JSON 截断（截断 JSON 被当整段结论回填 KP）。现为 4000 + 截断 JSON 的字段抠取。

**同步面**：`kpGraph.STALL_PROGRESS_TOOLS` 计入 `verify_original`（主动查证不算停滞）；
`STORY_LOOKUP_TOOL_NAMES` 自动放行（kpTurnService 特判执行，不进 rule-engine）。

## 2. 单测（26 项）

`server/src/rag/dossier/__tests__/originalLookup.spec.ts`：定位（锚点开窗/相交 gap/无锚与缺 gaps
安全返回/全局候选切块）、评分与预算（二元组评分排序/重叠不重复/≤预算/补足）、分层（scene→global→none）、
剧透 gate（问句敏感 / revealScene 锚点相交 / 普通问句）、渲染上限、端到端（一次 LLM 调用 +
messages 携带原文窗口与问题 / 缓存命中与 TTL 过期 / LLM 抛错、原文缺失、定位不到三类降级不抛出 /
截断 JSON 字段抠取 / JSON 骨架按失败 / 散文兜底 / -pro 模型守卫不发起调用）。

server 全量 `npx vitest run`：**550 通过**（含本工具 26）；`npx tsc --noEmit` 净。
（首轮全量曾出现 1 例 `storyParsers` PDF 用例并行超时，单独复跑 390ms 通过；后续两次全量均全绿。）

## 3. 离线工具直答（口径 (b)：全新上下文的事实核对）

harness：`scripts/eval/ab-verify-runtime.mjs`（直接调用**运行时代码**，deps 注入：原文=pdf-parse
纯文本、gaps/dossier=dossier-cache JSON；judge 与 P20–P23 同口径）。`--scene=auto` 用
`lexicalSearch(question)` 首个场景命中模拟"KP 在相关场景提问"，`--scene=none` 不给场景（走全篇兜底）。

| 剧本 | scene=auto（tier=scene） | scene=none（tier=global） | 窗口字符 | 中位延迟 |
|---|---|---|---|---|
| 火焰交织的盛夏 | 3.00（5×3，fab 0） | 3.00（5×3，fab 0） | ≈11.8k | auto 33s / none 22s |
| -营一日的恐怖 | **3.80**（5,5,3,3,3，fab 1） | 3.40（5,3,3,3,3，fab 0） | ≈11.7k | — |
| **pooled** | **3.40**（n=10，fab 1） | **3.20**（n=10，fab 0） | — | — |

**与历轮同口径对照**（同 judge、同探针）：

| 剧本 | P20 档案直答 | P24 档案直答 | P21 grid 回退 | P23 gaps 回退 | **P25 运行时工具（scene）** |
|---|---|---|---|---|---|
| 火焰交织的盛夏 | 2.60 | 3.60 | 3.40（n=5） | 3.67（n=3） | 3.00（n=5） |
| -营一日的恐怖 | 3.40 | 3.00 | 4.00（n=5，整篇 12.95k） | —（未重跑） | **3.80**（n=5） |

读法：
1. 运行时工具在 **12k 窗口、单次 LLM 调用、中位 22–33s** 的约束下，质量与 P24 档案直答同级
   （-营 3.80 vs 3.00 明显更好；火焰 3.00 vs 3.60 略差），并逼近 P21/P23 的离线回退
   （其窗口 15–18.5k，且带 dossier 触发逻辑）。**"运行时按需回退"在质量上站得住**。
2. scene 定向 vs 全局兜底：pooled 3.40 vs 3.20——**场景锚点略优但不显著**（与 P23"定位器平手"
   的结论一致）；代价是窗口更大、延迟 +11s。运行时保留 scene 优先的理由是延迟/相关性而非分数。
3. judge 的 3 分占绝大多数、note 多为"核心正确但细节超出摘录"——这是 judge 对"无法核验的额外
   细节"的保守扣分（P21/P23 同象），不代表编造；fab 仅 1 例（-营 天灾问）。

## 4. 回合级 A/B（口径 (a)：调用/命中/延迟）

harness：`scripts/eval/ab-compare.mjs` 真实模式（同一剧本、同一 10 回合脚本 + 每篇 5 条事实问，
rag 房 vs dossier 房；服务端 KP_WIRE_SAMPLING=1 + KP_CHUNK_STREAM=1）。两篇：火焰交织的盛夏、
-营一日的恐怖。输出 `training/eval/reports/ab-runtime-p25.json`，汇总脚本
`scripts/eval/ab-runtime-summary.mjs`。

### 4.1 房间级（20 个游玩回合，零失败）

| 剧本 | workflow | 回合 | TTFT p50/p95 | 整回合 p50/p95 | 回复 tok | 工具调用 |
|---|---|---|---|---|---|---|
| 火焰交织的盛夏 | rag | 10 | 39.3 / 110.8s | **74.3 / 117.8s** | 4,867 | skill_check×2, grant_clue×3, transition_scene×6, san_check×1 |
| 火焰交织的盛夏 | dossier | 10 | 22.5 / 45.1s | **31.7 / 51.5s** | 4,746 | skill_check×3, grant_clue×5, transition_scene×6, scene_list×4, scene_dossier×2, **verify_original×1** |
| -营一日的恐怖 | rag | 10 | 21.6 / 54.5s | **41.6 / 94.2s** | 8,072 | transition_scene×9, grant_clue×4, skill_check×2 |
| -营一日的恐怖 | dossier | 10 | 19.8 / 77.6s | **45.1 / 141.9s** | 4,923 | skill_check×1, grant_clue×3, scene_list×4, transition_scene×6, scene_dossier×4, san_check×1, adjust_san×1 |

**注入侧**：rag 房每回合 6.9–7.3k token 检索上下文（10 回合 68.9k/72.7k）；dossier 房是静态场景块
——按 P24 缓存档案实测 `buildSceneBlock` 平均 **1.0k（火焰）/1.3k（-营）token**，即 **≈6× 上下文缩减**
（ab-compare 本次的 dossier 注入列恒 0 是 harness 路径 bug，已在 P25 修正候选文件名，见提交）。

**延迟**：火焰篇 dossier 房整回合 p50 31.7s vs rag 74.3s（rag 每回合多注入 ~7k token 且更强推理）；
-营 篇两房持平（45.1s vs 41.6s），但 dossier 房 p95 差（141.9s vs 94.2s，两回合走了长工具链）。
**结论：dossier+工具的延迟不劣于 rag，高质量档下明显更优**；方差来自上游推理时长而非工具本身。

### 4.2 查证工具的实际调用（口径 (a) 的核心）

- 20 个游玩回合里 `verify_original` 只被调用 **1 次**（火焰篇；-营 篇 0 次），而同房的
  `scene_list`/`scene_dossier`/`lexical_search` 合计 14 次（另有事实回合里的 2–4 次）。
- **KP 明显偏好"查档案"而不是"查原文"**：档案能答的就停手，即使档案标着 coverage 31.1%/48.4%、
  8/4 条 coverage gap。查证工具的文档触发条件是"档案里没有、说不清、或需要原文级精确细节"，
  但 KP 不会主动判断"档案可能不全"。
- 因此 **P25 的 (a) 只拿到调用计数与延迟，没拿到有统计意义的房内命中率**：命中率改由离线直答
  harness 给出（10/10 全部成功产出结论：`ok=true`，tier 分布 scene 10/global 10；窗口 11.6–12.0k 字符，
  中位 22–33s）。房内命中率的采集重跑做过两次：第一次在 `rec.verifyResults` 捕获写入之前完成
  （只拿到调用计数）；第二次重跑被机器休眠中断（13:51→18:39 进程失联，无房间结果），
  **如实记录为未采到**——触发率修复后连同命中率一起在下一轮补测（见 §6）。
- 一个直接反证工具潜力的事实：-营 篇事实回合里，**档案房 KP 的房内回答 1.8 分，而同一批问题
  工具直答 3.4 分**（离线 harness，见 §3）——工具能答对的，KP 没去问。

## 6. 结论与遗留

### 结论

1. **运行时"原文查证"工具在质量上成立**：12k 窗口 + 单次全新上下文调用，离线直答 pooled 3.40
   （scene 定向）/3.20（全局兜底），与 P24 档案直答（3.0–3.6）同级、逼近 P21/P23 离线回退
   （3.4–4.0，窗口却是它的 2/3）；fab 仅 1/20。**"档案为主 + 运行时原文回退"这条路能走通**
   （P21 的架构假设在运行时被验证）。
2. **场景级定向的收益是"便宜"而不是"更准"**：scene vs global 分数 3.40 vs 3.20（P23 的"平手"结论
   在运行时复现），但 scene 定向窗口更贴当前剧情、语义相关性更好，延迟代价 +11s 可接受；保留
   scene 优先、global 兜底的分层。
3. **延迟/上下文明显改善**：dossier 房静态场景块 ≈1.0–1.3k token/回合 vs rag 6.9–7.3k token/回合
   （≈6×），整回合 p50 在火焰篇 31.7s vs 74.3s；-营 篇持平。工具调用回合（含一次 12k 窗口子调用）
   仍在同数量级。
4. **最大缺口是"触发率"，不是工具能力**：20 回合只调用 1 次；KP 偏好查档案（14 次）而不会自行判断
   "档案不全"。这是"档案房在对局内事实问答上弱于 rag 房"（-营 1.8 vs 3.8，与 P10 同向）的直接原因。
5. **工程约束落到位**：结果 ≤580 字符（会话 600 截断线内）、进程内 TTL 缓存、三类降级（原文缺失/
   定位不到/LLM 失败）不抛出、剧透层标注进提示词、-pro 模型守卫可执行可测。

### 遗留（按优先级）

1. **提高触发率（下一轮首选项）**：候选做法——(a) `scene_dossier`/`lexical_search` 空结果时追加
   "档案可能不全，可用 verify_original 查原文"提示；(b) 档案覆盖率低（<40%）时在知识源说明里
   把 verify_original 提为默认动作；(c) 服务端在"档案零命中 + 问题含事实名词"时自动预取一次查证
   结果注入（工具调用对玩家不可见）。建议先做 (a)，成本最低且直接对着观测到的行为。
2. **房内命中率与工具延迟未采到**（本轮调用太少 + harness 捕获落地晚于首跑）：下轮在触发率修复后
   用 `ab-compare` 的 wire 捕获（`rec.verifyResults`，P25b 已加）统计命中/未取得/剧透层占比与
   工具往返时延。
3. **A/B 只覆盖 2 篇**（篇幅成本：每篇含现场档案生成 ≈25–40 分钟）：结论方向可信，数字不宜当基线。
4. **judge 的"3 分墙"**：note 反复是"核心正确但细节超出摘录"——judge 对无法核验的额外细节保守扣分，
   导致 3 分区分度低；若要更细的度量，需要"逐要点核验"式 judge（P24 遗留同类问题）。
5. **剧透层标注未被实际触发验证**：本轮房内唯一那次调用不是剧透问句；离线 prompt 里 6/10 条带
   标注（词面信号 真相/结局 命中）。KP 是否**遵守**"禁止复述剧透层"没有直接证据（需专门的
   越权复述检测，见 P12/P15 的 fab 口径）。
